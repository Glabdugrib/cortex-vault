#HTN #CI #meeting

## <span style="color:rgb(255, 192, 0)">Stato attuale FE</span>
- <strong style="color:rgb(0, 176, 80)">build-and-publish.yaml</strong>: builda e pubblica immagini Docker (app + Prism) al push di `dev` e feature branches (`feat/`) e fix branches (`bugfix/` e `hotfix`).
- <strong style="color:rgb(0, 176, 80)">release-please.yaml</strong>: crea una release con [Release Please](https://github.com/joaquinjsb/gitea-release-please-action) su push su `main` e, se la release è nuova, builda e pubblica l’immagine Docker con la versione rilasciata.
- <strong style="color:rgb(0, 176, 80)">delete-tags.sh</strong>: lista e categorizza i tag Docker di un’immagine (`release`, branch correnti e orfani), mostra quelli eliminabili e, se confermato dall’utente, cancella i digest corrispondenti dal registry.

## <span style="color:rgb(255, 192, 0)">Proposte</span>
- [Trunk-based development](https://trunkbaseddevelopment.com/)
	- branch protection: solo PR verso `trunk` 
- Introduzione PRs
	- definire template
- **<strong style="color:rgb(0, 176, 80)">docker-cleanup.yaml</strong>:
	- trigger: daily/weekly
	- esegue lo script `delete-tags`
- **<strong style="color:rgb(0, 176, 80)">quality-check.yaml</strong>:
	- trigger: `pull_request` verso `trunk`
	- lint e unit/e2e tests
	- calcola coverage solo sui file modificati dalla PR
	- blocca merge se la coverage locale è sotto threshold
	- se supera la threshold, aggiunge mini-report alla PR
	- dependency check di `package.json` e `pnpm-lock.yaml`
	- possibilità di splittarlo in multipli workflow per esecuzione in parallelo: 
		- lint
		- unit-and-e2e-tests
		- coverage-check
		- dependecy-check
- <strong style="color:rgb(0, 176, 80)">coverage-report.yaml</strong>:
	- trigger: `pull_request` verso `trunk` approvata
	- genera coverage globale sull'intera codebase
	- aggiorna tool di reportistica esterni (?)`
	- avrebbe senso lanciarla periodicamente?
- <strong style="color:rgb(0, 176, 80)">ci-notifications.yaml</strong>:
	- trigger: PR open/update/accepted/failed/rejected
- <strong style="color:rgb(0, 176, 80)">release-notifications.yaml</strong>:
	- trigger: nuova release pronta (magari con changelog)
